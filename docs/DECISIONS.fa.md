# تصمیم‌های طراحی

برای هر تصمیم مشخص شده چه چیزی انتخاب شد، چه چیزی رد شد و چرا. منبع‌ها مستندات مایکروسافت هستند، مگر آنکه خلافش گفته شود. هر جا رفتاری به‌جای مستندات با آزمایش اندازه‌گیری شده، این موضوع ذکر شده است. نسخهٔ انگلیسی: [DECISIONS.md](DECISIONS.md).

## معماری

| موضوع | انتخاب | گزینهٔ ردشده و دلیل |
|---|---|---|
| ساختار | چهار پروژه با وابستگی‌هایی که کامپایلر تضمین می‌کند: Domain، Application، Infrastructure، Api | تک‌پروژه در این اندازه شدنی است، اما چیزی جلوی وابسته شدن قوانین دامنه به SQL را نمی‌گیرد. میکروسرویس هم اینجا توجیهی ندارد |
| Mediator | ندارد؛ endpointها مستقیم سرویس‌ها را صدا می‌زنند | MediatR با این تعداد کم use case فقط لایهٔ واسط و وابستگی اضافه می‌کند و سودی ندارد |
| Repository | یک port به نام `IAssignmentStore` که با کار واقعی سیستم نام‌گذاری شده | Repository عمومی نمی‌تواند عملیات اصلی، یعنی «واگذاری درخواست بعدی زیر قفل واگذاری»، را بیان کند |
| Mapping | متدهای کوچک `From` | AutoMapper تغییر فیلدها را از دید کامپایلر پنهان می‌کند |
| سبک API | Minimal API با `TypedResults` | Controller اینجا مزیت اضافه‌ای ندارد و نتایج نوع‌دار مستقیم به OpenAPI می‌رسند |
| اعتبارسنجی | `AddValidation` داخلی ‎.NET 10 با data annotation | FluentValidation برای چند قانون ساده یک وابستگی اضافه است |
| خطاها | یک `DomainRuleException` با کد ثابت که به Problem Details نگاشت می‌شود | کتابخانهٔ `Result<T>` برای چند خطای قانون کسب‌وکار، به همهٔ فراخوانی‌ها تشریفات اضافه می‌کند |
| زمان | `TimeProvider` که در تست‌ها جعلی می‌شود | با `DateTime.UtcNow` نمی‌توان سیاست گذر زمان را بدون sleep تست کرد |

## دیتابیس

**SQL Server** انتخاب شد، چون در پروژه‌های ‎.NET ترکیب رایجی است و سخت‌ترین نیازمندی مسئله را می‌شد اینجا روی آن به‌طور واقعی تست کرد. هر چیزی که مختص آن است در `SqlAssignmentStore` و migration قرار دارد. PostgreSQL هم با `pg_advisory_xact_lock` و `FOR UPDATE` به همین خوبی جواب می‌دهد.

- **کلیدهای identity از نوع `int` و `bigint`.** فشرده‌اند و درج در ایندکس خوشه‌ای ترتیبی می‌ماند. کلید خوشه‌ای `uniqueidentifier` پراکندگی ایجاد می‌کند و ترتیب مرتب‌سازی غیرشهودی دارد.
- **`OpenCount` یک ستون است، نه `COUNT(*)`.** مقدار محاسبه‌شده هرگز ناهماهنگ نمی‌شود، اما در آن صورت دیتابیس نمی‌تواند ظرفیت را تضمین کند. ستون امکان `CHECK (OpenCount <= Capacity)` را می‌دهد که حتی با وجود باگ در برنامه برقرار می‌ماند. این ستون فقط در همان تراکنش تغییر وضعیت درخواست نوشته می‌شود و یک تست آن را با تعداد واقعی مقایسه می‌کند.
- **ایندکس‌های فیلترشده روی ردیف‌های منتظر.** ایندکس‌های صف، هرچقدر هم تاریخچهٔ درخواست‌های بسته زیاد شود، کوچک می‌مانند.
- **موضوع‌ها کد معتبر هستند** (مثل `finance`)، نه متن آزاد. بنابراین تطبیق به collation یا تفاوت حروف فارسی و عربی مانند `ی`/`ي` وابسته نیست. اگر زمانی نام نمایشی لازم شد، باید در ستون جداگانه‌ای قرار بگیرد.
- **`RequestKey` از collation باینری استفاده می‌کند**، چون مقداری مبهم از سمت کلاینت است و `abc` و `ABC` دو کلید متفاوت‌اند.

## همزمانی: تصمیم اصلی

رویکرد انتخابی، یک قفل کوتاه در سطح برنامه دور هر واگذاری، به‌همراه قفل ردیفی روی کارشناسان درگیر است:

</div>

```text
1. Peek without locks: is anything servable? If not, stop, without ever queuing for the lock
2. In a transaction, take the dispatch lock: sp_getapplock, released at commit
3. Find the topic of the earliest servable request
4. Lock that topic's experts: UPDLOCK, using a pinned plan
5. Re-read their topics, then choose the best expert in C# (ExpertSelector)
6. Lock the head of that topic's queue, assign, and commit
```

<div dir="rtl">

**این طراحی، به‌خاطر نتیجهٔ اندازه‌گیری، طراحی اولیه‌ام را برگرداند.** در ابتدا قفل واحد را به‌عنوان گلوگاه رد کردم و فقط از قفل ردیفی روی کارشناسان استفاده کردم، با این انتظار که موضوع‌های بی‌ارتباط موازی اجرا شوند. تست بار نشان داد این اشتباه است:

| دو نمونه در Docker با ۶۴ کلاینت همزمان | فقط قفل ردیفی | قفل واگذاری |
|---|---|---|
| موضوع‌های دارای همپوشانی | ۳۷ درخواست در ثانیه، p95 برابر ۱۱٫۶ ثانیه | **۱۲۰ درخواست در ثانیه، p95 برابر ۱٫۲ ثانیه** |
| موضوع‌های بدون اشتراک، حالتی که قفل ردیفی باید برنده باشد | ۶۲ درخواست در ثانیه، p95 برابر ۶٫۹ ثانیه | **۱۱۵ درخواست در ثانیه، p95 برابر ۱٫۲ ثانیه** |
| هجوم ۲۵۶ کلاینت همزمان | ۶۳ درخواست در ثانیه، p99 برابر ۲۰٫۳ ثانیه | **۱۱۳ درخواست در ثانیه، p99 برابر ۷٫۴ ثانیه** |
| یک کارشناس پررقابت | ۱۴۳ درخواست در ثانیه، p95 برابر ۹۵۴ میلی‌ثانیه | ۱۱۲ درخواست در ثانیه، p95 برابر ۱٫۱ ثانیه |

علت، صف‌بندی قفل (lock convoy) بود: ۶۹٬۶۳۳ انتظار `LCK_M_U` برای حدود ۶۰۰۰ درخواست، و صفر deadlock. هر فراخوانی روی زودترین درخواست کل سیستم کار می‌کرد، پس همه به سراغ همان کارشناسان می‌رفتند، بیدار می‌شدند، می‌دیدند کار انجام شده و دوباره در صف می‌ایستادند. فقط حالت یک کارشناس، که عملاً از قبل یک قفل واحد بود، حدود ۲۰٪ سریع‌تر بود. قفل واگذاری کد را هم ساده‌تر کرد و ترتیب صف را در همهٔ موضوع‌ها دقیق کرد.

این عددها از یک لپ‌تاپ توسعه با Docker Desktop آمده‌اند، پس آن‌ها را نسبی بخوانید. اجراهای تکراری کد نهایی بین ۸۷ تا ۱۱۷ درخواست در ثانیه بود. محدودیت CPU نیست: یک واگذاری در هر لحظه یعنی یک flush لاگ در هر لحظه.

| گزینهٔ جایگزین | چرا انتخاب نشد |
|---|---|
| `lock` یا `SemaphoreSlim` درون پردازه | نیازمندی صریح اجرای دو نمونه از برنامه را برآورده نمی‌کند |
| قفل توزیع‌شده (Redis) | زیرساخت جدیدی برای نگهداری و نوع جدیدی از خرابی اضافه می‌کند، در حالی که دیتابیس همین حالا نقطهٔ هماهنگی است |
| فقط قفل ردیفی | در بالا اندازه‌گیری شد. طراحی اولیه بود |
| فقط `UPDATE ... WHERE OpenCount < Capacity` شرطی | ظرفیت را خوب حفظ می‌کند، اما دو واگذارکننده یک کارشناس را «کم‌بارترین» می‌خوانند و توزیع بار در همزمانی اشتباه می‌شود. یک تست تقسیم دقیق ۵/۵ را الزامی می‌کند |
| `rowversion` خوش‌بینانه با تکرار | دقیقاً در همان رقابتی که مسئله توصیف می‌کند، بیشتر تلاش‌ها شکست می‌خورند و تکرار می‌شوند |
| `SERIALIZABLE` | قفل‌های بازه‌ای انسداد و deadlock بیشتری می‌سازند. راهنمای deadlock مایکروسافت توصیه می‌کند در صورت نبود نیاز، از سطوح جداسازی بالاتر استفاده نشود |
| `READPAST` (رد کردن ردیف‌های قفل‌شده) | برای توان عملیاتی موازی خوب است، اما ممکن است یک واگذارکننده درخواست بعدی را بردارد، در حالی که درخواست جلوتر قفل است. اینجا ترتیب اولویت مهم‌تر است |
| Stored procedure | قوانین انتخاب را به SQL و دور از تست‌های واحد می‌برد |
| صف پیام با یک مصرف‌کننده | مشکل ترتیب را حل می‌کند، اما کلاینت دیگر کارشناس را در پاسخ نمی‌گیرد و broker به‌همراه outbox برای این نیاز زیادی است |

**چرا قفل ردیفی باقی مانده است.** بستن درخواست و ویرایش کارشناس قفل واگذاری را نمی‌گیرند تا بستن هرگز پشت واگذاری در صف نماند. این عملیات همان ردیف‌های کارشناس را تغییر می‌دهند، پس این ردیف‌ها همچنان باید قفل شوند.

**چرا plan کوئری کارشناسان ثابت شده است.** optimizer اگر آزاد باشد، روی جدول‌های کوچک clustered index scan انتخاب می‌کرد که روی تک‌تک کارشناسان `UPDLOCK` می‌گیرد و پشت هر کدام مسدود می‌شود. `FORCE ORDER`، `INNER LOOP JOIN` و `FORCESEEK` ابتدا ایندکس موضوع را می‌خوانند، پس فقط کارشناسان همان موضوع و همیشه به‌ترتیب id قفل می‌شوند.

**Deadlock.** واگذاری ابتدا قفل واگذاری، سپس کارشناسان به‌ترتیب id و بعد یک درخواست را می‌گیرد. عملیات بستن ابتدا درخواست خودش و سپس کارشناس آن را قفل می‌کند، اما درخواستی که هنگام بسته‌شدن کارشناس دارد در وضعیت `Assigned` است و واگذارکننده‌ها فقط با درخواست‌های `Pending` کار دارند. تست‌های بار صفر deadlock ثبت کردند. پشتیبان آن `EnableRetryOnFailure` است: هر تراکنش کامل، طبق راهنمای مایکروسافت برای connection resiliency، درون execution strategy و روی یک `DbContext` جدید اجرا می‌شود. نو بودن context مهم است، چون EF موجودیت‌های tracked را بازنویسی نمی‌کند و استفادهٔ دوباره از آن، مقادیر تازه‌ای را که قفل خوانده پنهان می‌کند.

**چرا موضوع‌ها پس از قفل دوباره خوانده می‌شوند.** این رفتار روی SQL Server 2025 با snapshot isolation روشن اندازه‌گیری شد: کوئری قفل‌گذاری که ابتدا `ExpertTopics` را بخواند و سپس منتظر قفل کارشناس بماند، موضوعی را برگرداند که در زمان انتظار حذف شده بود. دستور دوم موضوع‌های فعلی را می‌بیند. یک تست این حالت را پوشش می‌دهد و با حذف این بازخوانی، آن تست شکست می‌خورد.

**چرا پارامتر موضوع از نوع `varchar` تعریف شده است.** پارامترهای SQL خام به‌طور پیش‌فرض `nvarchar` هستند. در مقابل ستون `varchar`، این تبدیل index seek را به range scan روی همهٔ درخواست‌های منتظر تبدیل می‌کرد. با ۱۰۰٬۰۰۰ درخواست مسدود، کوئری سر صف ۶۰۵ خواندن هزینه داشت و توان عملیاتی به ۱۸ درخواست در ثانیه افتاد. با نوع درست، هزینه ۸ خواندن و توان عملیاتی ۱۱۷ درخواست در ثانیه است؛ همانند حالت بدون صف انباشته.

**خواندن برای پاسخ** پس از commit، لغو از سمت کلاینت را نادیده می‌گیرد. قطع ارتباط کلاینت، که خود سناریوی صورت مسئله است، نباید باعث رها شدن صف شود.

## سیاست صف

**انتخاب: یک امتیاز زمانی ثابت که فقط یک بار هنگام ساخت درخواست اعمال می‌شود.** درخواست فوری طوری رتبه می‌گیرد که انگار ۳۰ دقیقه زودتر رسیده است. این همان Earliest Deadline First با ددلاین‌هایی است که اختلاف ثابتی دارند.

| گزینهٔ جایگزین | چرا انتخاب نشد |
|---|---|
| اولویت مطلق | درخواست‌های عادی را برای همیشه منتظر می‌گذارد که مسئله آن را منع کرده است |
| ارتقا به فوری پس از N دقیقه | یک کار پس‌زمینه باید ردیف‌ها را بازنویسی کند و درخواست‌های ارتقایافته با فوری‌های واقعی بر اساس زمان رسیدن رقابت می‌کنند |
| نسبت وزن‌دار، مثلاً ۳ فوری به ازای ۱ عادی | به شمارندهٔ مشترک بین نمونه‌ها نیاز دارد و «عادی همچنان پشت ۳ فوری می‌ماند» هیچ حد زمانی نمی‌دهد |
| محاسبهٔ امتیاز گذر زمان هنگام کوئری | نمی‌تواند از ایندکس استفاده کند، پس هر برداشت از صف، کل صف را مرتب می‌کند |

ذخیرهٔ رتبه یعنی نه کار پس‌زمینه‌ای لازم است، نه وضعیت مشترک، و ایندکس مستقیماً ترتیب را می‌دهد. هزینه‌اش این است که تغییر مقدار امتیاز زمانی فقط روی درخواست‌های جدید اثر دارد؛ همین موضوع جایگاه درخواست‌های موجود را هم ثابت نگه می‌دارد.

## پایداری

**ابتدا commit، سپس واگذاری، به‌همراه sweeper.** واگذاری در همان تراکنش ساخت درخواست اتمی است، اما درخواست جدید می‌تواند زودتر از درخواست‌های منتظر قدیمی‌تر ظرفیت را بگیرد. شکست در واگذاری هم نباید ثبت درخواستی را که commit شده ناموفق نشان دهد، پس خطا ثبت می‌شود و sweeper دوباره تلاش می‌کند. در یک آزمایش chaos، کشتن یک نمونه در میانهٔ ترافیک نه درخواست قابل‌رسیدگی‌ای را منتظر گذاشت و نه هیچ قاعده‌ای را شکست.

**sweeper انتخاب رهبر ندارد**، چون `Dispatcher` خودش برای اجرای همزمان امن است. واگذاری هر درخواست HTTP به ۵۰ مورد محدود است تا افزایش ظرفیت یک کارشناس باعث کار نامحدود در یک فراخوانی نشود. بقیه را sweeper تمام می‌کند.

**Migration به‌صورت یک مرحلهٔ جدا و یک‌باره اجرا می‌شود**: سرویس `migrate` در Docker Compose و `--migrate-only` در جاهای دیگر. اجرای کانتینرهای واقعی دلیلش را نشان داد. اگر هر نمونه هنگام شروع روی سرور خالی migration اجرا کند، دو رقابت پیش می‌آید، چون قفل migration در EF Core داخل خود دیتابیس است و نمی‌تواند ساخت آن را پوشش دهد: نمونه‌ها روی `CREATE DATABASE` به هم می‌خوردند و گاهی `ALTER DATABASE ... READ_COMMITTED_SNAPSHOT` در EF به‌مدت ۶۰ ثانیه پشت اتصال نمونهٔ دیگر مسدود می‌شد و آن نمونه را از کار می‌انداخت. تلاش اول با retry فقط مشکل را پنهان کرد. با مرحلهٔ جدا، هر چهار شروع سرد بدون مشکل بود. گزینهٔ `MigrateOnStartup` فقط برای یک نمونه در محیط توسعه باقی مانده است.

**سطح جداسازی با migration تنظیم نمی‌شود.** نسخهٔ قبلی این کار را با `ROLLBACK IMMEDIATE` انجام می‌داد که می‌توانست در استقرار تدریجی، تراکنش‌های زندهٔ نمونه‌های دیگر را برگرداند. EF خودش این گزینه را روی دیتابیس‌هایی که می‌سازد فعال می‌کند. در غیر این صورت یک مرحلهٔ مستندشده برای اپراتور است و تست‌ها با هر دو حالت اجرا می‌شوند.

## تست

- **SQL Server واقعی، HTTP واقعی، دو نمونهٔ میزبانی‌شده، با sweeper خاموش**، مگر آنکه تست دربارهٔ خود آن باشد. providerهای حافظه‌ای قفل ندارند، پس نمی‌توانند نیازمندی همزمانی را بسنجند.
- **تست‌ها با خطای ثبت‌شدهٔ واگذاری شکست می‌خورند.** این خطاها عمداً به کلاینت برنمی‌گردند، پس بدون این بررسی، constraint نوع `CHECK` می‌توانست خراب بودن قفل‌گذاری را بی‌صدا پنهان کند.
- **بررسی با mutation.** با حذف قفل واگذاری و قفل‌های ردیفی، ۶ مورد از ۱۲ تست همزمانی شکست می‌خورند، از جمله تست ۲۰ درخواست برای ظرفیت ۵ در هر دو سطح جداسازی. با حذف بازخوانی موضوع‌ها، تست مربوط به آن شکست می‌خورد.
- **فراتر از مجموعهٔ تست، در Docker:** تست بار تا ۲۵۶ کلاینت همزمان، صف انباشتهٔ ۱۰۰٬۰۰۰ درخواستی، شروع سرد و کشتن یک نمونه، که پس از هر کدام قواعد با SQL بررسی شدند.
- **xUnit v3** روی Microsoft.Testing.Platform، با assertionهای خود xUnit. نسخهٔ جدید FluentAssertions برای استفادهٔ تجاری به مجوز پولی نیاز دارد.
- **CI** پروژه را می‌سازد، همهٔ تست‌ها را روی Linux با Testcontainers اجرا می‌کند، به‌روز بودن migrationها را بررسی می‌کند و image را می‌سازد.

## محدودیت‌های شناخته‌شده

این موارد عمداً ذکر شده‌اند تا بتوان دربارهٔ آن‌ها گفت‌وگو کرد، نه اینکه بعداً کشف شوند.

- **واگذاری‌ها در کل سیستم پشت سر هم انجام می‌شوند**؛ حدود ۱۰۰ مورد در ثانیه روی لپ‌تاپ آزمایش. این مقدار بسیار بیشتر از ظرفیت کارشناسان انسانی است و به همین دلیل اینجا مصالحهٔ درستی است. اگر روزی محدودیت شد، گام بعدی یک قفل برای هر گروه از کارشناسانِ دارای موضوع مشترک است، آن هم پس از اندازه‌گیری.
- **تأخیر درخواست با همزمانی رشد می‌کند**، چون فراخوانی‌ها منتظر نوبت می‌مانند: p50 حدود ۳۰ میلی‌ثانیه با ۴ کلاینت، حدود ۴۰۰ میلی‌ثانیه با ۶۴ و حدود ۲ ثانیه با ۲۵۶. انتقال واگذاری به یک worker پس‌زمینه ثبت را فوری می‌کند، اما کلاینت دیگر کارشناس را در پاسخ نمی‌بیند.
- **واگذارکنندهٔ منتظر یک اتصال از pool را نگه می‌دارد.** هجوم ۲۵۶ کلاینت خطایی ایجاد نکرد. هجومی فراتر از ظرفیت pool باعث شکست برخی واگذاری‌ها می‌شود که ثبت و توسط sweeper تمام می‌شوند. قفل واگذاری حداکثر ۲۰ ثانیه منتظر می‌ماند.
- **از دست رفتن commit هنگام تکرار درج.** اگر اتصال درست پس از commit موفق قطع شود، تکرار به ایندکس یکتا می‌خورد، پاسخ به‌جای `201` برابر `200` می‌شود و درخواست تا ۳۰ ثانیه منتظر sweeper می‌ماند. داده‌ها درست‌اند.
- **ساعت‌ها.** رتبه‌ها از ساعت برنامه می‌آیند، پس ساعت نمونه‌ها باید همگام باشد. چند ثانیه اختلاف در برابر امتیاز ۳۰ دقیقه‌ای ناچیز است.
- **غیرفعال کردن کارشناس، درخواست‌های باز او را دوباره واگذار نمی‌کند.** مسئله این را نخواسته و تصمیمی محصولی است.
- **خارج از محدوده:** احراز هویت و مجوزدهی که پیش از هر استفادهٔ واقعی لازم‌اند، و همچنین metrics و tracing فراتر از لاگ ساختاریافته و health check.
