# مسیریابی درخواست‌ها (Request Routing)

این سیستم درخواست‌های ورودی را به‌صورت خودکار به کارشناس مناسب واگذار می‌کند و در ترافیک همزمان و با اجرای چند نمونه از برنامه روی یک دیتابیس مشترک هم درست کار می‌کند.

فناوری‌ها: ‎.NET 10، ASP.NET Core Minimal APIs، EF Core 10 و SQL Server.

همهٔ تصمیم‌های طراحی به‌همراه گزینه‌های بررسی‌شده در [docs/DECISIONS.fa.md](docs/DECISIONS.fa.md) آمده‌اند. نسخهٔ انگلیسی این راهنما: [README.md](README.md).

## راه‌اندازی سریع

به ‎.NET 10 SDK و یکی از این دو نیاز دارید: SQL Server محلی یا Docker.

**اجرا روی SQL Server محلی.** تنظیمات Development از `Server=.` با احراز هویت ویندوز استفاده می‌کند و دیتابیس در اولین اجرا ساخته می‌شود.

</div>

```bash
dotnet run --project src/RequestRouting.Api
```

<div dir="rtl">

مستندات API در مسیر `/scalar` (فقط در Development) و نمونه‌فراخوانی‌ها در [api.http](api.http) است.

**اجرای دو نمونه با Docker:** پورت‌های 5001 و 5002 از یک SQL Server مشترک استفاده می‌کنند. ابتدا یک سرویس یک‌بارهٔ `migrate` دیتابیس را آماده می‌کند.

</div>

```bash
docker compose up --build
```

<div dir="rtl">

**اجرای تست‌ها.** تست‌ها از SQL Server واقعی استفاده می‌کنند، چون قفل‌گذاری واقعی را می‌سنجند. یا متغیر زیر را به یک سرور اشاره دهید، یا آن را تنظیم نکنید تا یک کانتینر Testcontainers بالا بیاید (نیاز به Docker دارد). هر تست دیتابیس `RequestRoutingTest_<guid>` خودش را می‌سازد و در پایان حذف می‌کند.

</div>

```bash
ROUTING_TEST_SQLSERVER="Server=.;Trusted_Connection=True;TrustServerCertificate=True" dotnet test --solution RequestRouting.slnx
```

<div dir="rtl">

**مشاهدهٔ نیازمندی ۲ با دو پردازهٔ واقعی** (Windows PowerShell و SQL Server محلی). این اسکریپت ۲۰ درخواست همزمان و ۲۰ تکرار را برای کارشناسی با ظرفیت ۵ می‌فرستد و در پایان دیتابیس خود را حذف می‌کند.

</div>

```bash
powershell -ExecutionPolicy Bypass -File scripts/two-instances-demo.ps1
```

## API

| متد | مسیر | کاربرد |
|---|---|---|
| `POST` | `/api/requests` | ثبت درخواست. `201` اگر جدید باشد، `200` اگر `requestKey` از قبل وجود داشته باشد، `409` اگر آن کلید برای درخواست دیگری استفاده شده باشد |
| `GET` | `/api/requests/{id}` | خواندن یک درخواست |
| `POST` | `/api/requests/{id}/close` | بستن درخواست و واگذاری درخواست بعدی. تکرار آن بی‌خطر است |
| `GET` | `/api/requests/pending?take=50` | صف انتظار، به همان ترتیبی که پردازش خواهد شد |
| `POST` | `/api/experts` | ساخت کارشناس |
| `GET` | `/api/experts/{id}` | خواندن یک کارشناس |
| `PATCH` | `/api/experts/{id}` | تغییر ظرفیت، وضعیت فعال بودن یا تخصص‌ها. ممکن است درخواست‌های منتظر را واگذار کند |
| `GET` | `/health/live`, `/health/ready` | سلامت برنامه، و آمادگی آن به‌همراه دسترسی به دیتابیس |

خطاها با قالب Problem Details (RFC 9457) برمی‌گردند. تعارض با قوانین کسب‌وکار یک کد ثابت در فیلد `type` دارد؛ مثلاً `urn:request-routing:request-key-reused`.

## قوانین

### انتخاب کارشناس

از میان کارشناسان فعالی که تخصص مرتبط و ظرفیت آزاد دارند:

۱. **کمترین نسبت درخواست باز به ظرفیت.** مثال صورت مسئله: ۲ از ۴ یعنی ۰٫۵ و ۳ از ۱۰ یعنی ۰٫۳، پس کارشناس دوم انتخاب می‌شود.

۲. **در صورت تساوی، کارشناسی که آخرین واگذاری‌اش قدیمی‌تر است**؛ کارشناسی که هنوز درخواستی نگرفته در اولویت است.

۳. **اگر باز هم مساوی بودند، کمترین شناسه (id).**

**دلیل این قانون تساوی.** تساوی رایج است، چون همهٔ کارشناسان بیکار با نسبت صفر مساوی‌اند. اگر فقط یک ترتیب ثابت داشتیم، همیشه یک نفر برنده می‌شد و شناسه‌های کوچک‌تر همیشه زودتر کار می‌گرفتند. انتخاب «بیکارترین» کار را در طول زمان، شبیه round-robin، عادلانه پخش می‌کند و چون از همان فیلد `LastAssignedAt` استفاده می‌کند، به وضعیت اضافه‌ای نیاز ندارد. شناسه فقط برای کامل کردن ترتیب است تا همهٔ نمونه‌های برنامه به یک تصمیم برسند و تست‌ها تکرارپذیر باشند. انتخاب تصادفی رد شد، چون قابل بازتولید نیست.

اگر هیچ کارشناسی واجد شرایط نباشد، درخواست در وضعیت `Pending` می‌ماند.

### ترتیب صف

هر درخواست هنگام ساخته‌شدن یک **رتبه** می‌گیرد و صف به‌ترتیب صعودی رتبه پردازش می‌شود:

</div>

```text
Normal: rank = created time
Urgent: rank = created time - 30 minutes   (Queue:UrgentHeadStart)
```

<div dir="rtl">

با درخواست فوری طوری رفتار می‌شود که انگار ۳۰ دقیقه زودتر رسیده است. **مثال** با یک کارشناس مشغول:

| درخواست | زمان ثبت | رتبه |
|---|---|---|
| N1 عادی | 10:00 | 10:00 |
| U1 فوری | 10:05 | 09:35 |
| U2 فوری | 10:20 | 09:50 |
| U3 فوری | 10:31 | 10:01 |

ترتیب پردازش: **U1، U2، N1، U3**. درخواست‌های U1 و U2 طبق انتظار از N1 جلو می‌زنند. U3 وقتی می‌رسد که N1 بیش از مقدار امتیاز زمانی منتظر مانده است، پس N1 زودتر پردازش می‌شود.

- **اولویت فوری بر عادی:** هر درخواست فوری از درخواست‌های عادی‌ای که کمتر از ۳۰ دقیقه از آن قدیمی‌ترند جلو می‌زند.
- **عادی برای همیشه منتظر نمی‌ماند:** درخواست عادی‌ای که در زمان T ثبت شده، فقط از درخواست‌های فوری ثبت‌شده پیش از T + ۳۰ دقیقه عقب می‌افتد. تعداد این درخواست‌ها محدود است، پس هرچقدر هم جریان درخواست‌های فوری ادامه پیدا کند، نوبت درخواست عادی می‌رسد.
- **هیچ درخواستی صف را مسدود نمی‌کند:** فقط موضوع‌هایی بررسی می‌شوند که کارشناس آزاد دارند، پس از درخواستی که کسی نمی‌تواند به آن رسیدگی کند به‌سادگی عبور می‌شود. این درخواست به‌محض آزاد شدن کارشناس مرتبط واگذار می‌شود.

تنظیم این سیاست فقط یک عدد است: مقدار `0` یعنی نوبت‌دهی سادهٔ «اول بیا، اول برو» و مقدار بزرگ‌تر یعنی اولویت قوی‌تر برای درخواست فوری.

### حفظ صحت در همزمانی

| تضمین | روش | پشتیبان در دیتابیس |
|---|---|---|
| ظرفیت هرگز بیشتر از حد مجاز نمی‌شود | در هر لحظه فقط یک واگذاری زیر `sp_getapplock` انجام می‌شود و روی کارشناسان هم `UPDLOCK` گرفته می‌شود، چون عملیات بستن آن قفل را نمی‌گیرد | `CHECK (OpenCount <= Capacity)` |
| هر درخواست فقط یک کارشناس دارد | ردیف درخواست در حالت `Pending` قفل می‌شود و فقط یک ستون `ExpertId` دارد | `CHECK` که `Status` را به `ExpertId` گره می‌زند |
| `RequestKey` یکسان، یک درخواست | درج انجام می‌شود و تکراری بودن به‌عنوان تکرار همان درخواست در نظر گرفته می‌شود | ایندکس یکتا روی `RequestKey` |
| کارکرد با چند نمونه از برنامه | همهٔ هماهنگی در دیتابیس است و هیچ چیز در حافظهٔ پردازه نیست | |

هر درخواست ابتدا با وضعیت `Pending` درج می‌شود و تنها یک `Dispatcher` حق واگذاری دارد. ساخت درخواست، بستن آن و تغییر کارشناس همگی **ابتدا commit و سپس واگذاری** را انجام می‌دهند. به این ترتیب تغییری که آخر از همه commit می‌شود همهٔ تغییرهای دیگر را می‌بیند و هیچ رویدادی از دست نمی‌رود. اگر پردازه‌ای بین commit و واگذاری از کار بیفتد، یک sweeper که روی همهٔ نمونه‌ها اجرا می‌شود درخواست را ظرف ۳۰ ثانیه بازیابی می‌کند.

### رفتار اندازه‌گیری‌شده

دو نمونه و SQL Server در Docker Desktop روی یک لپ‌تاپ توسعه، پس این عددها را نسبی بخوانید. پس از هر اجرا، بیشتر شدن از ظرفیت، شمارنده‌های اشتباه و کلیدهای تکراری بررسی شد: هیچ‌کدام وجود نداشت و deadlock هم رخ نداد.

| سناریو | توان عملیاتی | p50 | p95 | خطا |
|---|---|---|---|---|
| ۴ کلاینت همزمان | ۹۳ درخواست در ثانیه | ۳۰ میلی‌ثانیه | ۷۳ میلی‌ثانیه | ۰ |
| ۶۴ کلاینت همزمان، موضوع‌های دارای همپوشانی | ۱۰۱ درخواست در ثانیه | ۴۰۱ میلی‌ثانیه | ۱٫۲ ثانیه | ۰ |
| ۶۴ کلاینت همزمان، با ۱۰۰٬۰۰۰ درخواست مسدود در انتظار | ۱۱۷ درخواست در ثانیه | ۳۵۸ میلی‌ثانیه | ۱٫۲ ثانیه | ۰ |
| هجوم ۲۵۶ کلاینت همزمان | ۸۷ درخواست در ثانیه | ۲٫۲ ثانیه | ۶٫۸ ثانیه | ۰ |

تست بار طراحی را تغییر داد: قفل ردیفی به‌تنهایی روی کاغذ مقیاس‌پذیرتر به نظر می‌رسید، اما در اندازه‌گیری تا ۳ برابر کندتر بود. مقایسه را در [DECISIONS.fa.md](docs/DECISIONS.fa.md) ببینید.

## نکات عملیاتی

**Snapshot isolation.** دیتابیس‌هایی که EF Core می‌سازد به‌صورت خودکار `READ_COMMITTED_SNAPSHOT ON` دارند. برای دیتابیسی که به روش دیگری ساخته شده، دستور زیر را در بازهٔ نگهداری اجرا کنید، چون تراکنش‌های باز را برمی‌گرداند. صحت سیستم به این تنظیم وابسته نیست و تست‌های همزمانی با هر دو حالت اجرا می‌شوند، اما انسداد بین خواننده و نویسنده را کاهش می‌دهد.

</div>

```sql
ALTER DATABASE CURRENT SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;
```

<div dir="rtl">

**Migrationها.** با چند نمونه، `--migrate-only` را یک بار به‌عنوان مرحله‌ای از استقرار و پیش از شروع آن‌ها اجرا کنید، همان‌طور که Docker Compose انجام می‌دهد. گزینهٔ `Database:MigrateOnStartup` در تنظیمات Development فقط برای یک نمونه روشن است: رقابت نمونه‌ها برای ساخت دیتابیس می‌تواند باعث از کار افتادن آن‌ها شود.

</div>
